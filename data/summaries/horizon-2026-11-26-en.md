**Why it matters:** Because Washington bars Samsung, SK hynix and Micron from selling HBM into China, domestic AI accelerator designers — Huawei designs its own HBM but does not say who manufactures it — have no confirmed volume supplier of the memory their chips need, which keeps HBM the binding constraint on China&\#x27;s AI hardware output even as commodity DRAM and NAND capacity surges. For memory buyers, the concrete near-term signal is supply: CXMT&\#x27;s Shanghai fab is scheduled to take delivery of tools in the second half of 2026 with volume in 2027, and YMTC&\#x27;s third Wuhan fab is expected to reach about 50,000 wafers a month by 2027, with roughly half of that output earmarked for DRAM rather than NAND.

**What to watch:** CXMT&\#x27;s president says the company&\#x27;s first 4F² product, a server DDR5 RDIMM, is due by year-end 2026 — a test of how far it can scale without EUV lithography. Whether CXMT&\#x27;s reported HBM3E risk production converts into qualified mass output, which the report flags as possible in 2027, is the other checkable milestone.

### [Nfs2root: 12-year-old pre-auth root flaw reported in Linux kernel NFS server](https://opensec.in/blog/nfs2root-cve-2026-99362) ⭐️ 7.0/10

A writeup published on opensec.in under the name &quot;nfs2root&quot; \(CVE-2026-99362\) describes a pre-authentication remote root vulnerability in the Linux kernel&\#x27;s NFS server that the author says went unnoticed for 12 years. If accurate, an attacker who can reach an exposed NFS service could gain root-level access without first authenticating. As of the discussion around the report, no proof-of-concept code had been posted and the flaw had not been independently reproduced, so the severity rests on the author&\#x27;s account rather than a public exploit. Commenters reading the report believe it concerns NFS 4.1 and 4.2 rather than all NFS versions, which would narrow the set of affected servers.

Hacker News · dm · Nov 25, 20:35 · [Discussion](https://news.ycombinator.com/item?id=50647161)

**Verified and unconfirmed:** Verified: OpenSec&\#x27;s report, which labels the issue CVE-2026-99362, describes a 12-year-old pre-authentication remote root vulnerability in the Linux kernel&\#x27;s NFS server; its detection guidance checks whether nfsd is loaded, whether NFSv4.1 or 4.2 is enabled, and whether port 2049 is reachable on a non-loopback address.

Not yet confirmed: A Hacker News commenter said no proof-of-concept was posted, and another described disabling NFSv4.1/4.2 via /proc/fs/nfsd/versions as a temporary workaround; the report does not provide exploit evidence or a full technical write-up, and independent testing, practical exploitability, and whether that workaround fully closes the issue are unconfirmed.

**Background:** NFS \(Network File System\) is the long-standing protocol Linux uses to share directories over a network, and the server side of it, \`nfsd\`, runs inside the kernel itself — so a flaw there sits below authentication and below any userspace service an administrator could restart. The vulnerability, tracked as CVE-2026-99362 and dubbed NFS2ROOT, is an out-of-bounds write involving a sequence buffer bounds check; it is present in kernel releases that do not yet carry the corrected check and resolved in newer ones that do, according to vulnerability trackers. Red Hat&\#x27;s analysis team, in an assessment dated November 19, 2026, listed the flaw against its products and said a fix may be released in the near future, meaning distribution patch coverage is still being worked out.

**Why it matters:** Operators running kernel NFS servers that answer NFS 4.1 or 4.2 should treat internet- or tenant-reachable exports as untrusted until their distribution ships a fix, and long-term-support or out-of-support kernels may lag. One commenter described a temporary workaround: stopping the NFS server and restricting the enabled minor versions with \`echo &quot;-4.1 -4.2&quot; \| sudo tee /proc/fs/nfsd/versions\`, noting the change reverts on reboot and should first be checked against clients that actually negotiate those versions.

**What to watch:** Watch for kernel updates or distribution advisories referencing CVE-2026-99362, and for a public proof-of-concept or independent reproduction, which would settle the open questions about affected versions and reachability.

**Community discussion:** Commenters focused on mitigation rather than the flaw&\#x27;s mechanics: one reported running NFSv4 behind spiped, another proposed the version-disable workaround above and checked which clients actually used 4.1 or 4.2 first, and a third pointed out that no proof-of-concept had been published — an assessment of the disclosure, not evidence the bug is harmless. A side thread argued the episode shows AI-assisted code review finding long-lived bugs that human review missed.

### [DeepMind reports AlphaProof Code proof of Signal&\#x27;s libsignal binary](https://www.tomshardware.com/tech-industry/artificial-intelligence/google-deepmind-ai-engineers-conjure-mathematical-proof-of-signals-encryption-protocol-alphaproof-code-framework-powered-human-bot-cooperation-for-speedy-work) ⭐️ 7.0/10

Google DeepMind released a paper and GitHub repository describing AlphaProof Code, a framework it says produced a complete formal proof that an Arm-compiled AArch64 \(64-bit Arm\) binary of Signal&\#x27;s libsignal library, plus minimal scaffolding, matches a revised specification. The work used Lean, generating about 1.2 million lines of proofs for the cryptographic protocol and 5.3 million lines to show each binary instruction matched formal models of AArch64, CPU and Linux process behavior; agents flagged 1% of the codebase for human review. The result covers libsignal&\#x27;s cryptographic engine as compiled for Arm, not the Signal app as a whole, and the article reports no independent validation of the proof.

Tom&\#x27;s Hardware · Nov 25, 12:00

**Verified and unconfirmed:** Verified: Google DeepMind published a paper and GitHub repository for AlphaProof Code and reported a complete Lean proof of an Arm-compiled AArch64 libsignal binary. Not yet confirmed: independent replication of the proof and DeepMind&\#x27;s claim that the method generalizes to other software at practical cost.

**Background:** Formal verification means proving in machine-checked logic that an implementation matches a written specification; it has historically been so labor-intensive that the seL4 microkernel&\#x27;s proof reportedly took about 20 years and the CompCert C compiler&\#x27;s about six. The proofs in this effort are written in Lean, the same proof assistant AI systems have recently used for mathematics: AI Daily Radar&\#x27;s November 23 digest reported that OpenAI&\#x27;s GPT-6.2 Astra produced a machine-verifiable Lean proof of Smoktunowicz&\#x27;s gap theorem. AlphaProof Code shifts that approach from proving mathematical theorems to proving that a compiled AArch64 binary of libsignal matches a specification.

**Why it matters:** Developers of security-critical software can inspect a public workflow for proving a compiled binary against a specification, including Lean models of AArch64 instructions, registers, memory and Linux processes; the assurance stops at libsignal&\#x27;s cryptographic engine, so it is not a whole-app security audit.

**What to watch:** Watch for independent review or replication of the public Lean proof, or a second binary verified with AlphaProof Code; the report gives no timeline for either.
